# Mini NPU Simulator

입력 패턴과 필터를 **같은 위치끼리 곱하고 모두 더하는 MAC(Multiply-Accumulate) 연산**으로
십자가(Cross)와 X 모양을 판별하는 Python 콘솔 프로그램입니다.

실제 NPU는 수천 개의 MAC 회로로 곱셈-누적을 **동시에(병렬로)** 처리합니다. 이 시뮬레이터는 같은 연산을
for문으로 **하나씩(순차로)** 실행하면서, 패턴 크기(N)가 커질 때 연산 시간이 N²에 비례해 늘어나는 것을 측정합니다.

- 개발 환경: Python 3.8 이상 (검증: Windows 11, Python 3.14)
- 사용 라이브러리: 표준 라이브러리만 사용 (`json`, `time`, `math`, `os`, `sys`, `unicodedata`, `unittest`). NumPy 등 외부 라이브러리는 사용하지 않습니다.

## 실행 방법

```bash
git clone https://github.com/light-456/npu-sim.git
cd npu-sim
python main.py
```

프로젝트 루트에서 실행해야 `src` 패키지를 찾을 수 있습니다. `data.json`은 `main.py`와 같은 폴더에서 읽습니다.

| 입력 | 동작 |
|------|------|
| `1` | **사용자 입력 모드(3×3)**: 필터 A, B와 패턴을 한 줄씩 공백으로 구분해 입력합니다. 필터 입력 방식에서 Enter를 누르면 직접 입력하고, `g`를 누르면 패턴 생성기가 A=십자가, B=X 필터를 자동으로 만듭니다. |
| `2` | **data.json 분석 모드**: 필터 로드 → 패턴 검증·판정 → 성능 분석 → 결과 요약 순서로 실행합니다. |

```bash
python main.py data_error.json   # 다른 JSON 파일을 분석 (실행 후 2 선택)
python -m unittest -v            # 자동 테스트 12개 실행
python -m tools.make_data        # data_sample.json / data_error.json 재생성 (data.json은 건드리지 않음)
```

### 실행 예시 (모드 1)

```
필터 입력 방식 - Enter: 직접 입력 / g: 십자가(A)·X(B) 자동 생성
선택:
필터 A (3줄 입력, 공백 구분)
0 1 0
1 1
입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.
[필터 A] 처음부터 다시 입력하세요.
...
# [3] MAC 결과
A 점수: 1
B 점수: 5
연산 시간(평균/10회): 0.0008 ms
판정: B
```

점수 차이가 1e-9보다 작으면 `판정: 판정 불가 (|A-B| < 1e-09)`로 출력합니다.
예를 들어 필터 A `0.1 0.2 0 / 0 0 0 / 0 0 0`, 필터 B `0.3 0 0 / 0 0 0 / 0 0 0`, 패턴 전부 1을 입력하면
A 점수는 `0.30000000000000004`, B 점수는 `0.3`이 되어 판정 불가로 처리됩니다.

## data.json 구조

```json
{
    "meta": { "version": "1.0", "type": "json" },
    "filters": {
        "size_5":  { "cross": [[...5x5...]],  "x": [[...5x5...]] },
        "size_13": { "cross": [[...13x13...]], "x": [[...13x13...]] },
        "size_25": { "cross": [[...25x25...]], "x": [[...25x25...]] }
    },
    "patterns": {
        "size_5_1": { "input": [[...5x5...]], "expected": "x" },
        "size_5_2": { "input": [[...5x5...]], "expected": "+" },
        "...": "size_13_1, size_13_2, size_25_1, size_25_2"
    }
}
```

| 항목 | 규칙 | 프로그램 처리 |
|------|------|---------------|
| `filters` 키 | `size_{N}` | `split("_")[1]`로 N을 꺼내 필터 크기로 사용 |
| `filters` 값 | `cross`, `x` 키 아래 N×N 실수 배열 | 키를 Cross/X로 정규화하고 N×N 숫자 배열인지 검증 |
| `patterns` 키 | `size_{N}_{idx}` | N을 꺼내 같은 크기의 필터 선택. 규칙 위반이면 FAIL |
| `input` | N×N 2차원 배열 | 키의 N과 실제 크기가 일치하는지 검증 |
| `expected` | `'+'`, `'x'` 등 | Cross/X로 정규화한 뒤 판정과 비교 |
| `meta` | - | 사용하지 않음 |

## 구현 요약

| 항목 | 구현 방식 |
|------|-----------|
| 데이터 구조 | 2차원 리스트. `[[0]*n]*n`은 모든 행이 같은 리스트를 공유하므로, 컴프리헨션으로 행마다 새 리스트를 만듭니다. `get_value`/`set_value`로 특정 위치를 읽고 씁니다. |
| MAC 연산 | 이중 for문으로 `total += pattern[i][j] * filt[i][j]`를 N²번 반복합니다. 정수와 실수를 모두 처리합니다. |
| 라벨 정규화 | `strip().lower()` 후 매핑합니다. `'+'`, `'cross'`는 `Cross`, `'x'`는 `X`, 그 외는 `None`(FAIL)입니다. 콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨로 합니다. |
| 동점 정책 | `EPSILON = 1e-9`. `abs(a - b) < EPSILON`이면 `UNDECIDED`(모드 1은 "판정 불가")로 판정합니다. |
| 입력 검증 (모드 1) | 줄마다 숫자 개수와 숫자 변환(`nan`/`inf` 거부)을 검사합니다. 틀리면 안내 후 해당 행렬을 처음부터 다시 입력받습니다. |
| 예외 처리 (모드 2) | 파일 없음, JSON 손상은 안내 후 종료합니다. 키 규칙 위반, 크기 불일치, 알 수 없는 라벨, 필터 없음, 숫자가 아닌 값은 케이스 단위로 FAIL과 사유를 기록하고 계속 진행합니다. |
| 실패 분류 | 실패마다 `데이터/스키마`, `로직`, `수치 비교` 중 하나의 태그를 붙여 출력합니다. |
| 성능 측정 | `time.perf_counter()`로 `mac()` 호출 구간만 측정합니다. 워밍업 1회 후 10회 반복 평균(ms)을 구하며, 입출력과 파일 읽기는 측정에서 제외합니다. |

| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS | - |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS | - |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL | 수치 비교 |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL | 수치 비교 |

### 실패 원인 분석

실패 원인은 **데이터/스키마 문제**, **로직 문제**, **수치 비교 문제** 세 가지로 나누어 진단했습니다.

**1. 수치 비교 문제 (3건): 설계된 동점**

실패 3건은 모두 두 필터 점수가 수학적으로 똑같도록 만들어진 케이스입니다.
공식 data.json의 필터는 가운데 칸만 다른 값(0.9, 7.5, 4.9)을 가지고 있어, 특정 패턴에서 두 점수가 같아집니다.

| 케이스 | Cross 필터와 겹치는 칸 | X 필터와 겹치는 칸 | 수학적 점수 |
|--------|----------------------|-------------------|------------|
| size_5_1 (X 패턴) | 가운데 1칸 × 0.9 = 0.9 | 대각선 9칸 × 0.1 = 0.9 | 0.9 = 0.9 |
| size_13_2 (십자가 패턴) | 십자가 25칸 × 0.3 = 7.5 | 가운데 1칸 × 7.5 = 7.5 | 7.5 = 7.5 |
| size_25_1 (X 패턴) | 가운데 1칸 × 4.9 = 4.9 | 대각선 49칸 × 0.1 = 4.9 | 4.9 = 4.9 |

컴퓨터는 0.1, 0.3 같은 소수를 2진수로 정확히 저장하지 못합니다. 그래서 같은 값을 여러 번 더하면 아주 작은 오차가 쌓입니다.
0.1을 9번 더하면 `0.8999999999999999`, 0.3을 25번 더하면 `7.499999999999997`, 0.1을 49번 더하면 `4.899999999999999`가 됩니다.
반면 한 칸만 곱한 쪽(0.9, 7.5, 4.9)은 오차가 없어서, 두 점수가 1e-16~1e-15만큼 어긋납니다.

`==`나 `>`로 그대로 비교했다면 이 오차 때문에 한쪽이 "이긴" 것으로 판정됩니다.
size_5_1과 size_25_1은 Cross가 이겨 expected(X)와 다른 판정이 나오므로 **로직 오류처럼 보이는 FAIL**이 됩니다.
size_13_2는 X 점수가 아주 조금 커서 X로 판정되므로 역시 FAIL이 됩니다.
어느 쪽이든 판정 결과가 데이터의 뜻이 아니라 **부동소수점 오차에 따라 우연히 정해집니다.**

epsilon(1e-9) 정책을 적용해 세 케이스를 모두 `UNDECIDED`로 판정했습니다.
expected에는 Cross 또는 X만 있으므로 결과는 FAIL이지만, 이는 프로그램 결함이 아니라 **동점 규칙에 따른 정상 동작**입니다.
1e-9는 누적 오차(약 1e-16~1e-15)보다 충분히 크고, 동점이 아닌 케이스의 실제 점수 차이(최소 8.8)보다는 충분히 작아서
"오차로 인한 차이"와 "진짜 차이"를 안정적으로 구분합니다.

**2. 데이터/스키마 문제 (공식 데이터 0건)**

공식 data.json의 expected는 `'+'`와 `'x'`, 필터 키는 `'cross'`와 `'x'`로 적혀 있습니다.
라벨 정규화로 모두 `Cross`/`X`로 통일한 뒤 비교했기 때문에 표기 차이로 인한 FAIL은 없습니다.
정규화 없이 비교했다면 `"Cross" == "+"`(표기 차이)와 `"X" == "x"`(대소문자 차이)가 모두 거짓이 되어, PASS 3건까지 전부 FAIL(총 6건 실패)이 되었을 것입니다.

스키마 검증은 `data_error.json`으로 따로 확인했습니다. 4가지 오류가 모두 프로그램 중단 없이 케이스 단위 FAIL과 사유로 기록됩니다.

| 케이스 | 의도한 오류 | 출력된 사유 |
|--------|-----------|------------|
| size_5_9 | 5×5 키에 13×13 배열 | 패턴 크기 불일치 (키는 5x5) |
| pattern_1 | 키 형식 위반 | 키 규칙 위반 (size_{N}_{idx} 형식이 아님) |
| size_13_9 | expected가 `'circle'` | 알 수 없는 expected 라벨: 'circle' |
| size_7_1 | 7×7 필터가 없음 | size_7 필터 없음 |

**3. 로직 문제 (0건)**

동점이 아닌 3건(size_5_2, size_13_1, size_25_2)은 모두 expected와 일치해 MAC 연산과 판정 로직이 올바름을 확인했습니다.
또 `tests/test_simulator.py`의 자동 테스트 12개(미션 예시 점수 5/1, 정규화, epsilon, 크기 검증, 오류 데이터 처리 등)가 모두 통과합니다.

### 시간 복잡도 분석

| 크기(N×N) | 연산 횟수(N²) | 평균 시간(ms) | 3×3 대비 시간 | 3×3 대비 N² |
|-----------|--------------|---------------|---------------|-------------|
| 3×3 | 9 | 0.0008 | 1배 | 1배 |
| 5×5 | 25 | 0.0019 | 약 2.4배 | 약 2.8배 |
| 13×13 | 169 | 0.0086 | 약 10.8배 | 약 18.8배 |
| 25×25 | 625 | 0.0299 | 약 37.4배 | 약 69.4배 |

(워밍업 1회 후 각 크기 10회 반복 평균. 측정 환경: Windows 11, Python 3.14. 절대값은 실행 환경마다 다릅니다.)

1. MAC 연산은 N×N의 모든 칸을 정확히 한 번씩 방문하며, 칸마다 곱셈 1번과 덧셈 1번을 합니다. 연산 횟수가 N²이므로 시간 복잡도는 **O(N²)**입니다.
2. 측정 결과도 크기가 커질수록 시간이 꾸준히 증가합니다. 큰 크기끼리 비교하면 N²에 가깝게 늘어납니다. 13×13 → 25×25에서 N²은 약 3.7배, 시간은 약 3.5배 늘었습니다.
3. 3×3 대비 25×25는 N² 비율(69배)보다 작은 약 37배로 측정됩니다. 작은 크기에서는 함수 호출, 반복문 준비, `perf_counter` 호출 같은 **고정 비용**이 전체 시간에서 차지하는 비중이 크기 때문입니다.
4. 시간을 `고정 비용 + (칸당 비용 × N²)`으로 보면, N이 커질수록 고정 비용 비중이 줄어 측정값이 N² 비율에 점점 가까워집니다.
5. 1회 측정은 편차가 크므로 10회 평균을 사용했습니다. 측정 구간에는 `mac()` 호출만 두었고, 입출력과 파일 읽기는 제외했습니다. 첫 호출의 준비 비용이 섞이지 않도록 워밍업 1회는 측정하지 않았습니다.
6. N이 2배가 되면 연산량은 4배가 됩니다. 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로, CPU처럼 순차로 처리하면 연산량을 감당하기 어렵습니다. 그래서 MAC을 병렬로 처리하는 NPU가 필요합니다.

## 보너스 과제

### 1. 시뮬레이터 최적화: 1차원 배열

2차원 리스트를 길이 N²의 1차원 리스트로 펼친 뒤(`flatten`), 단일 for문으로 MAC을 계산합니다(`mac_flat`).
모드 2 실행 시 동일 입력, 동일 반복 횟수(10회)로 비교한 표가 함께 출력됩니다. 펼치는 시간은 측정에서 제외했습니다.

| 크기 | 2차원(ms) | 1차원(ms) | 속도 향상 |
|------|-----------|-----------|-----------|
| 3×3 | 0.0008 | 0.0005 | 1.79배 |
| 5×5 | 0.0019 | 0.0011 | 1.65배 |
| 13×13 | 0.0086 | 0.0059 | 1.46배 |
| 25×25 | 0.0299 | 0.0231 | 1.29배 |

- 2차원 접근 `pattern[i][j]`는 행 리스트를 찾은 뒤 다시 칸을 찾아야 해서 인덱싱이 2번 필요합니다. 1차원 `pattern[k]`는 1번이면 됩니다.
- 안쪽 반복문을 N번 새로 시작하는 비용도 없어져 약 1.3~1.8배 빨라졌습니다.
- 연산 횟수는 그대로 N²이므로 시간 복잡도는 여전히 O(N²)입니다. 상수 비용만 줄어든 것입니다.
- 크기가 커질수록 속도 향상 폭이 줄어드는 이유는, 곱셈-누적 자체의 비용이 차지하는 비중이 커지기 때문입니다.

### 2. 패턴 생성기
